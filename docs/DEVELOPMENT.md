# Техническая документация (DEVELOPMENT)

Утилита миграции истории Telegram-каналов в мессенджер MAX. Реализована как CLI-приложение на **Node.js (ESM, v20.6+)** без сторонних npm-зависимостей (используются только встроенные `fetch`, `FormData`, `Blob`, `node:fs`, `node:path`, `node:util` и флаг `--env-file`).

---

## 1. Архитектура и структура проекта

```text
tg-to-max/
├── src/
│   ├── index.js        # Точка входа: парсинг CLI-флагов, preflight, dry-run, основной цикл, ретраи, SIGINT
│   ├── parser.js       # Чтение result.json, HTML-конвертация, маппинг медиа, алгоритм склейки альбомов
│   ├── maxClient.js    # HTTP-клиент MAX Bot API: auth, 2-шаговый upload, обработка attachment.not.ready, split >4000
│   ├── state.js        # Атомарное чтение/запись чекпоинта (state.json)
│   ├── logger.js       # Одновременное логирование в stdout/stderr, import.log и failed.json
│   └── check.js        # Диагностический скрипт: GET /me, поиск chat_id через GET /updates, --send-test
├── .env.example        # Шаблон переменных окружения
├── .env                # Локальные секреты (в .gitignore)
├── .gitignore
├── package.json        # "type": "module" и npm-скрипты
├── README.md           # Пользовательская документация
└── DEVELOPMENT.md      # Этот файл
```

### Принцип хранения состояния (Portable State)
Служебные файлы не хранятся в директории скрипта, а создаются внутри `ARCHIVE_DIR`:
```text
<ARCHIVE_DIR>/_max_import/channel_<sanitized_MAX_CHANNEL_ID>/
├── state.json
├── import.log
└── failed.json
```
* Исходные файлы экспорта Telegram открываются строго **read-only**.
* Изоляция по `channel_<ID>` позволяет прогонять один и тот же архив сначала в тестовый канал, затем в боевой без ручной очистки стейта.
* Запись `state.json` выполняется **атомарно** (`writeFile(state.json.tmp)` → `rename`), что исключает повреждение файла при аварийном завершении процесса.

## 2. Парсинг экспорта Telegram (`src/parser.js`)

### Особенности `result.json` из Telegram Desktop
1. **Фильтрация и порядок:** берутся только записи `msg.type === 'message'` (служебные события `type: "service"` отбрасываются), сортировка строго по `id` по возрастанию.
2. **Полиморфное поле `text`:** в JSON Telegram `text` может быть строкой или массивом строк и объектов-сущностей (`{ type, text, href }`).
   * Текст конвертируется в **HTML** (`format: "html"` в MAX), а не в Markdown. Причина: в произвольных постах часто встречаются символы `*`, `_`, `~`, `[`, которые ломают Markdown-парсер. В HTML достаточно экранировать `&`, `<`, `>` (и `"` в `href`).
   * Поддерживаемые теги MAX HTML: `<b>`, `<i>`, `<s>`, `<u>`, `<code>`, `<pre>`, `<a href="...">`. Цитаты (`blockquote`) рендерятся как `<i>&gt; ...</i>`.
3. **Заглушки пропущенных файлов:** если файл не был скачан Telegram (превышен лимит размера или пользователь нажал «Пропустить»), в полях `photo`/`file` лежит строка в скобках вида `"(File unavailable, please try again later)"`. Функция `isTelegramPlaceholder()` отлавливает такие значения до обращения к ФС.
4. **Стикеры:** `media_type === 'sticker'` (`.tgs`/`.webp`) исключаются, так как не поддерживаются API MAX как изображения.

### Алгоритм склейки альбомов (`groupMessagesIntoPosts`)
Telegram Desktop не включает поле `grouped_id` в JSON-экспорт, раскладывая элементы альбома подряд как отдельные сообщения. Эмпирически подтверждённые инварианты альбома:
* Соседние элементы имеют совместимый тип (`image` или `video`), включая элементы с `notExportedReason`, чтобы не разрывать альбом надвое из-за одного пропущенного фото.
* Разница `date_unixtime` между соседними элементами: `Math.abs(next.ts - current.lastTs) <= 2` сек (10-фото альбом часто пересекает границу 1 секунды).
* Лимит элементов в альбоме: `MAX_ALBUM_SIZE = 10` (ограничение Telegram; MAX принимает до 12 вложений `image`/`video` в одном сообщении).
* **Инвариант подписи:** в альбоме текст присутствует максимум у одного элемента — либо у первого, либо у последнего.
  * Два элемента, у которых **оба** имеют непустой текст, никогда не объединяются.
  * Если текст появился у элемента, присоединяемого к группе с пустым текстом (подпись на последнем фото), группе выставляется `closed = true`, чтобы следующее сообщение гарантированно начало новый пост.
* Каждый сгруппированный пост имеет `startId` и `endId`. В `state.json` сохраняется `lastProcessedId = post.endId`, что обеспечивает совместимость с перезапуском и ручным `--from-id`.

## 3. Нюансы интеграции с MAX Bot API (`src/maxClient.js`)

Интеграция выполнена строго по актуальной спецификации `dev.max.ru`:

### Базовый URL, TLS и авторизация
* **Base URL:** `https://platform-api2.max.ru` (старый `platform-api.max.ru` выведен из эксплуатации).
* **TLS / НУЦ Минцифры:** домен использует российский корневой сертификат, отсутствующий во встроенном CA-хранилище Node.js. Передаётся через переменную окружения `NODE_EXTRA_CA_CERTS` (формат PEM). При TLS-ошибке клиент перехватывает `err.cause.code` и выводит диагностическое сообщение.
* **Авторизация:** заголовок `Authorization: <token>` **без** префикса `Bearer` (query-параметр `access_token` больше не поддерживается).
* **Получение `chat_id`:** эндпоинт `GET /chats` удалён из API; `src/check.js` извлекает `chat_id` каналов из `GET /updates?timeout=5` (события `bot_admin_permissions_changed`, `bot_added` и др.).

### 2-шаговая загрузка медиа (`POST /uploads`)
1. **Шаг 1:** `POST /uploads?type={image|video|audio|file}` (устаревший тип `photo` не используется — только `image`).
   * Для `video` и `audio` токен вложения возвращается **на шаге 1** (`{ url, token }`).
   * Для `image` и `file` на шаге 1 возвращается только `{ url }`.
2. **Шаг 2:** `POST <upload_url>` с `multipart/form-data`, имя поля строго `data`.
   * Заголовок `Content-Type` вручную **не задаётся** — `fetch` + `FormData` в Node.js генерирует корректный `boundary` сам.
   * Для `image` передаётся заголовок `Authorization: <token>`, ответ имеет вид `{ photos: { "<key>": { token: "..." } } }`.
   * Для `file` ответ `{ fileId, token }`.
   * Для `video` и `audio` сервер отвечает не JSON, а XML-строкой `<retval>1</retval>`, поэтому парсинг JSON обёрнут в `try/catch`, а токен берётся с шага 1.
3. **Ограничение имени файла:** MAX отклоняет имена > 200 символов; `sanitizeFileName()` обрезает имя до 180 символов с сохранением расширения.

### Отправка сообщений (`POST /messages`) и обработка ошибок
* **Эндпоинт:** `POST /messages?chat_id=<id>`, тело `{ text, format: "html", attachments }`.
* **Асинхронная обработка медиа (`attachment.not.ready`):** после загрузки файла серверу MAX требуется время на процессинг. Клиент выдерживает начальную паузу (1.2с для фото, 3.5с для видео/аудио/файлов) и при получении ошибки `attachment.not.ready` повторяет **только `POST /messages`** с тем же токеном по расписанию `[3, 5, 8, 12, 20, 30]` сек — без повторной загрузки файла.
* **Лимит текста (4000 символов):** `splitTextChunks()` разрезает текст по ближайшему `\n` или пробелу. Первая часть уходит с `attachments`, остальные — следом с паузой 1с.
* **Лимиты MAX (проверяются в `index.js` и `--dry-run`):**
  * `image`: 50 МБ (`jpg`, `jpeg`, `png`, `gif`, `tiff`, `bmp`, `heic`)
  * `video`: 250 МБ (`mp4`, `mov`, `mkv`, `webm`)
  * `audio`: 256 МБ
  * `file`: 4 ГБ
  * Частота: до 2 сообщений/сек в один канал (управляется `DELAY_MS`, по умолчанию 2000 мс) + автоматическая обработка `HTTP 429` по заголовку `Retry-After`.

## 4. Надёжность и отказоустойчивость (`src/index.js`)

* **Fail-fast preflight:** в боевом режиме перед циклом вызывается `GET /me` (моментальная проверка токена и TLS-сертификата).
* **Частичная деградация внутри альбома:** если 1 файл из альбома отсутствует на диске или превышает лимит размера MAX, он логируется в `failed.json`, но остальные валидные файлы альбома и текст всё равно публикуются.
* **Ретраи (`withRetries`):** до 3 попыток на сетевые ошибки, `429` и `5xx`. На фатальные `401` (неверный токен) и `415` (неподдерживаемый тип медиа) ретраи не выполняются.
* **Graceful shutdown:** перехват `SIGINT` (`Ctrl+C`) выставляет флаг `stopRequested`, завершает текущую итерацию, сохраняет `state.json` и закрывает файловый поток `import.log` в блоке `finally`. Повторный `Ctrl+C` выполняет немедленный выход (`process.exit(1)`).

## 5. Идеи для доработки (Roadmap)

* **Resumable upload для тяжёлых файлов (> 100 МБ):** сейчас `uploadMedia()` читает файл целиком в буфер через `fs.readFile()`. Для очень больших файлов/видео можно перейти на потоковую/чанковую загрузку (`Content-Range`), поддерживаемую MAX API.
* **Сохранение `reply_to_message_id`:** ведение маппинга `tg_id -> max_message_id` в `state.json` для сохранения связей ответов внутри канала.
* **Автоматическая подстановка `NODE_EXTRA_CA_CERTS`:** запуск через небольшой wrapper-скрипт или флаг `--use-system-ca` (доступен в Node.js 22.15+/24+, если корневой сертификат Минцифры установлен в системное хранилище ОС).
* **Веб-интерфейс (опционально):** `parser.js` и `maxClient.js` не завязаны на CLI — поверх них легко поднять локальный Express-сервер с SSE-стримингом логов и управлением паузой.
